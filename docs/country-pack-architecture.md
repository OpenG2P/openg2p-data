# Country packs — target architecture

**Status:** agreed direction, not yet built. Records the decisions so far and the
questions still open.

## Objective

Instantiate a registry for a country by naming one thing: its **country pack**.

A registry's *structure* is hardcoded in its extension — tables, fields,
relationships, validation rules, reports. That is the product, and it does not
vary by country. Everything the registry *contains* comes from the pack.

```
openg2p-data/packs/<CODE>  →  CDS  →  registry seeds from CDS at install
```

## The split

| Hardcoded in the registry extension | From the country pack |
|---|---|
| Tables, columns, relationships | Administrative hierarchy and P-codes |
| Field definitions, validation rules | Boundary geometry for maps |
| Reports and reporting views | Code lists — gender, crop, livelihood, programme… |
| Bulk data generator | Sample individuals and households |

The pack is expected to grow. Anything that varies by country belongs in it.

## Country Data Service

Master Data Service becomes the runtime home of a pack. **"Country Data Service
(CDS)" is proposed** — it describes the role better than "master data" once packs
carry code lists and sample people, not just geography. Naming not settled.

CDS is the only component that needs the pack itself. Registry images stay
country-agnostic: install NSR for a different country by pointing it at a CDS
seeded with a different pack — no registry rebuild.

Boundary GeoJSON stays in object storage with the URI recorded against each unit
(already implemented). It is bulk binary fetched whole by the browser, not
something to serve from an API or store in rows. Spatial *queries* — "which
woreda is this GPS point in?" — are a separate capability; PostGIS is available
in the cluster but not installed.

## Two tiers of data, with different obligations

**Sample data — must be coherent with the pack.** A few dozen individuals and
their households, checked into the pack. Names, phone formats and addresses match
the country. This is what demos show, what smoke tests assert on, and what a
person actually reads. Coherence matters because incoherence is visible — today's
fixture has American names living in Swahili-named villages.

**Bulk data — need not be coherent.** Tens of thousands of records generated by
the registry at install, purely so reports and dashboards have something to show.
Nobody reads an individual row. Names and phone numbers need not belong to the
country, so **one bulk generator serves every instantiation** of a given registry.

What the bulk generator *does* need from the pack is **geography** — every record
must point at a real administrative unit, or maps and drill-downs break. It also
needs the code lists, so the values it writes are ones the deployment recognises.

This removes a problem we had otherwise designed around: no per-country name
pools are needed for bulk generation, and Faker's uneven locale coverage (its
`am_ET` silently returns American names) only matters when authoring the small
sample set.

## Install sequence

1. CDS is seeded from the pack — geography, code lists, sample people
2. Registry db-seed waits for CDS, then copies code lists into its own
   `g2p_attribute_values` and loads the sample records
3. Registry validates locally against its copy — CDS is an **install-time**
   dependency, never a per-write one
4. Registry generates bulk data, reading geography and code lists from CDS

An ordering guard already exists for step 2 (`require-mds-geo`). The registry must
also **assert** that CDS holds the pack it expects rather than assume it — CDS
already stamps a pack `version` on every geo row.

## Consequences to work through

**Python enums must go for anything the pack defines.** Today 31 enum classes in
the NSR extension restate code lists for API validation. They are compiled into
the image, so they cannot be reseeded, and they make one image unable to serve two
countries — `ProgramEnum` hardcodes Ethiopia's `UPSNP`/`RPSNP`.

A universal-superset enum was considered and rejected: gender is the counter-example,
where countries define genuinely different taxonomies rather than subsets of one.
So these become plain strings validated against the seeded attribute values. DB
columns are already `String`, so no migration is needed — the enums are only type
hints plus Pydantic validation.

**Validation moves rather than disappears.** Two checks replace the compiled one:
`validate_pack.py` gains code-list checks (build time, no database), and a
post-seed check confirms what landed matches what the pack declared.

**Decided — semantic role tags.** Reporting views reason about *meaning*, not just
values: `is_head = (relationship_to_head = 'SELF')`,
`is_displaced = (displacement_status <> 'HOST_COMMUNITY')`. With country-defined
lists those literals break silently — exactly how `is_head` came to read zero for
every household.

So a value may carry `roles`, and platform logic asks for the role rather than the
literal. `packs/roles.json` is the closed vocabulary and the only source of it:
each role names the attribute expected to carry it and whether **one** value holds
it (`head_of_household`) or **many** may (`improved_water`, since which sources
count as improved is a national definition).

`validate_pack.py` reads that file and rejects an unknown role, a single-value
role held twice, and — the case that matters — a role **no value carries** while
its list is present. That last check was missing at first, and its absence was the
same silent-zero shape as the bug it exists to prevent.

**Open — where domain lists sit.** Crops vary by domain *and* country, so a
`domains/<domain>/` subtree within the pack keeps one artifact per country without
every install loading every domain's lists.

## Already done

- Packs are the only supported route for geography; `geoSeed.countryPack` is the
  single declaration of a country
- NSR's bulk generator, its distributions and extract query moved into NSR, beside
  the enums and reporting views they depend on
- `validate_pack.py` enforces the pack contract in CI
